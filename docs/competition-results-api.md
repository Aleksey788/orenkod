# Результаты соревнований и протоколы

Модуль использует Laravel Session, cookies и CSRF в `routes/web.php`. Для JSON-запросов передавайте `Accept: application/json` и `Content-Type: application/json`. Все даты API имеют ISO 8601, время PDF явно помечено часовым поясом приложения (`config/app.php`, сейчас UTC).

## Обнаруженная схема и совместимость

- `competitions` уже содержит дисциплину, тип, возрастную группу, уровень, формат, даты и `protocol_path`.
- Результат связан с соревнованием и спортсменом через `competition_application_id`. Прямых `competition_id` и `athlete_id` в `competition_results` нет, новые дублирующие столбцы не добавляются.
- Существующие уникальные ограничения `competition_applications(competition_id, athlete_id)` и `competition_results(competition_application_id)` исключают дубликаты в PostgreSQL.
- Сохраняются `score decimal(12,2)`, `place`, `notes`, `entered_by_user_id`, timestamps. В JSON используется `result_status`, в БД - `status`.
- Дополнительная миграция `database/migrations/2026_10_28_104834_add_results_publication_to_competitions_table.php` добавляет `results_published_at` (индекс), `results_published_by_user_id` (nullable FK на users), меняет значение статуса результата по умолчанию с `ranked` на `finished`. Старые записи не изменяются. Если ранее вручную создавались записи `ranked`, администратор должен проверить и пересохранить их с явным статусом до публикации.
- Публикация соревнования (`status=published`) и публикация результатов (`results_published_at`) имеют разный смысл.
- Уже существующие `AuditLog`/`audit_logs` используются для `result.created`, `result.updated`, `protocol.previewed`, `protocol.generated`, `results.published`. Фиксируются пользователь, активная роль, сущность, время и разрешённые значения; секреты не записываются.
- Обнаружена историческая несовместимость миграций users: начальная миграция уже создаёт ФИО, а `2026_10_27_134500_update_users_table.php` повторно добавляет эти поля и удаляет отсутствующее `name`. Старые миграции сохранены. Тесты модуля поднимают только необходимые актуальные миграции в SQLite в памяти, обходя этот исторический конфликт. Это не проверка полной установки проекта с нуля.
- Исправлены `UserFactory` (ФИО вместо отсутствующего `name`) и подключение `HasFactory` у User.

## Маршруты

`{competition}` - ID существующего соревнования. У административных маршрутов middleware `auth`, `verified`, `role:admin`; недостаточно просто иметь роль, она должна быть активной в сессии.

| Метод | URL | Доступ | Ответ 200 |
| --- | --- | --- | --- |
| GET | `/admin/competitions/{competition}/participants` | Активный admin, подтверждённый email | Все одобренные участники с имеющимися результатами |
| GET | `/admin/competitions/{competition}/results` | Активный admin, подтверждённый email | Итоговая таблица, включая незаполненные результаты |
| PUT | `/admin/competitions/{competition}/results` | Активный admin, подтверждённый email | Массовое сохранение, затем итоговая таблица |
| GET | `/admin/competitions/{competition}/protocol` | Активный admin, подтверждённый email | PDF: черновой предпросмотр либо сохранённый официальный файл |
| POST | `/admin/competitions/{competition}/results/publish` | Активный admin, подтверждённый email | Публикация PDF и результатов, затем итоговая таблица |
| GET | `/competitions/{competition}/results` | Публично после публикации результатов | Итоговая таблица |
| GET | `/competitions/{competition}/protocol` | Публично после публикации результатов | PDF-вложение |
| GET | `/athlete/results?page=1` | `auth`, `verified`, `role:athlete` | История текущего спортсмена, 15 записей на странице |

PDF хранится на отдельном диске `protocols` под `storage/app/private/protocols`. Для диска отключена раздача файлов. `storage:link` для протоколов не требуется. API выдаёт URL контроллера, а не путь в хранилище. ФИО и организация являются публичными данными итоговой таблицы; email, телефон, дата рождения, примечания и данные сессии не возвращаются.

## Правила ввода и мест

Ввод и публикация доступны только у соревнования со статусом `published`, у которого `ends_at` уже наступило. PUT принимает от 1 до 1000 результатов, каждый спортсмен должен иметь одобренную заявку именно этого соревнования. Для больших соревнований вводите несколько пакетов до публикации. PUT обновляет только переданные результаты и не удаляет остальные.

```json
{
  "results": [
    {"athlete_id": 1, "score": 95.5, "place": 1, "result_status": "finished"},
    {"athlete_id": 2, "score": 88, "place": 2, "result_status": "finished"},
    {"athlete_id": 3, "score": null, "place": null, "result_status": "dns"},
    {"athlete_id": 4, "score": 10, "place": null, "result_status": "dnf"},
    {"athlete_id": 5, "score": null, "place": null, "result_status": "dsq"}
  ]
}
```

| Статус | Значение | Место | Баллы |
| --- | --- | --- | --- |
| `finished` | Завершил | Обязательно, целое от 1 до 2147483647 | Обязательны |
| `dns` | Не стартовал | Только null или отсутствие | Необязательны |
| `dnf` | Не завершил | Только null или отсутствие | Необязательны |
| `dsq` | Дисквалифицирован | Только null или отсутствие | Необязательны |

Баллы - число от -9999999999.99 до 9999999999.99, максимум два десятичных знака. Отрицательные и нулевые баллы допустимы. Ответы возвращают десятичную строку (например, `"95.50"`) для сохранения точности.

Места задаются официально администратором. Совпадающие места разрешены и обозначают официально разделённое место. Система не определяет победителя по баллам и не изменяет вручную выставленные места. Равные баллы не требуют равных мест: дисциплины могут иметь дополнительные критерии. Порядок: `finished` по месту, затем остальные; при равенстве - ФИО, ID спортсмена. `position` означает строку таблицы, `place` - официальное место. Этот порядок одинаков для API и PDF, подходит для всех шести дисциплин.

Повторяющийся `athlete_id` в одном пакете отклоняется. Повторный PUT обновляет запись, не создавая дубль; точное повторение не создаёт лишнего аудита. Пакет проверяется и сохраняется целиком в транзакции. ID администратора берётся из сессии. Вложенные произвольные поля отклоняются; служебные поля публикации и `entered_by_user_id` передавать нельзя.

Пример ответа GET/PUT/POST публикации (значения ID и дат условны):

```json
{
  "data": [
    {
      "id": 11,
      "position": 1,
      "competition_id": 7,
      "competition_application_id": 21,
      "athlete_id": 1,
      "full_name": "Иванов Иван Иванович",
      "organization": "Учебная организация",
      "discipline": {"id": 1, "name": "Программирование алгоритмическое"},
      "score": "95.50",
      "place": 1,
      "result_status": "finished",
      "created_at": "2026-10-28T10:00:00+00:00",
      "updated_at": "2026-10-28T10:00:00+00:00"
    }
  ],
  "meta": {
    "competition_id": 7,
    "results_published_at": "2026-10-28T11:00:00+00:00",
    "protocol_url": "http://orenkod.local/competitions/7/protocol"
  }
}
```

До публикации `meta.results_published_at` и `meta.protocol_url` равны null. Для незаполненного участника `id`, `score`, `place`, `result_status` и timestamps равны null; он остаётся в таблице.

Пример элемента `/participants`:

```json
{
  "data": [
    {
      "competition_application_id": 21,
      "athlete_id": 1,
      "full_name": "Иванов Иван Иванович",
      "organization": "Учебная организация",
      "discipline": {"id": 1, "name": "Программирование алгоритмическое"},
      "application_status": "approved",
      "result": null
    }
  ]
}
```

При наличии результата `result` содержит объект той же формы, что элемент итоговой таблицы. Связи загружаются заранее, без запроса на каждого участника.

## Публикация и PDF

`POST /admin/competitions/7/results/publish` не требует тела. Должен существовать хотя бы один одобренный участник, у каждого нужен корректный результат. Для отсутствовавшего спортсмена явно укажите `dns`. Старый неизвестный статус, неполная запись либо результат неодобренной заявки блокируют публикацию с 422.

Сохранение, публикация, подача и рассмотрение заявок используют общую блокировку строки соревнования. После публикации PUT результатов и изменение состава заявок блокируются. Повторный POST публикации возвращает существующую публикацию без замены PDF, новых результатов или повторных событий публикации.

PDF создаётся Dompdf 3.1.6 из `resources/views/competitions/protocol.blade.php`, формат A4 альбомный, встроенный DejaVu Sans с кириллицей, повторяемый заголовок таблицы. Включены данные соревнования, все допущенные участники, баллы, места, статусы, дата формирования и счётчики. Назначенные судьи берутся из `judge_assignments` с их фактическими должностями и ФИО. При отсутствии назначений выводится незаполненный реквизит. Подписи не имитируются. HTML-значения экранируются Blade; сетевые ресурсы, PHP и JavaScript у Dompdf отключены.

Черновой PDF помечен как проект и отдаётся только администратору с `Cache-Control: private, no-store`, без сохранения публичного файла. При публикации записывается отдельный закрытый файл и в одной транзакции фиксируются путь, дата, администратор и аудит. Если запись БД/аудита не удалась, новый файл удаляется. При ошибке генерации публикация не происходит. Официальный PDF скачивается как `protocol-{id}.pdf` через контроллер.

В MVP официальное исправление/отзыв публикации намеренно отсутствует: опубликованные результаты заморожены. Для будущих исправлений необходим отдельный процесс с аудитом и новой версией PDF; обычный PUT для этого не подходит. Рейтинг не рассчитывается: исходные баллы отделены от будущих рейтинговых, сезон определяется по дате соревнования, дисциплина/уровень доступны через связи.

## История спортсмена

`GET /athlete/results` определяет спортсмена исключительно через `$request->user()->athlete`. Параметр `athlete_id` не используется. Показываются только одобренные заявки с официально опубликованными результатами, новые соревнования идут первыми по `starts_at`, при равенстве - ID результата. Страница содержит 15 записей. При отсутствии профиля либо результатов возвращается пустая пагинация с 200.

```json
{
  "data": [
    {
      "id": 11,
      "competition": {
        "id": 7,
        "title": "Кубок ОренКод",
        "discipline": {"id": 1, "name": "Программирование алгоритмическое"},
        "starts_at": "2026-10-26T09:00:00+00:00",
        "ends_at": "2026-10-27T18:00:00+00:00",
        "competition_type": {"id": 1, "name": "Личное первенство"},
        "level": "regional"
      },
      "score": "95.50",
      "place": 1,
      "result_status": "finished",
      "results_published_at": "2026-10-28T11:00:00+00:00",
      "protocol_url": "http://orenkod.local/competitions/7/protocol"
    }
  ],
  "links": {
    "first": "http://orenkod.local/athlete/results?page=1",
    "last": "http://orenkod.local/athlete/results?page=1",
    "prev": null,
    "next": null
  },
  "meta": {
    "current_page": 1,

    "last_page": 1,
    "path": "http://orenkod.local/athlete/results",
    "per_page": 15,
    "to": 1,
    "total": 1
  }

```

Laravel может включать дополнительные поля `meta` пагинации. Фильтры дисциплины/сезона/статуса пока не реализованы; запрос истории изолирован в сервисе для дальнейшего расширения.

## Ошибки

| Код | Причина |
| --- | --- |
| 401 | Нет авторизованной сессии на защищённом маршруте |
| 403 | Нет нужной активной роли либо email не подтверждён |
| 404 | Соревнование отсутствует; публичные результаты ещё не опубликованы; отсутствует официальный PDF |
| 419 | Отсутствует/устарел CSRF-токен или cookie сессии для изменяющего запроса |
| 422 | Ошибка валидации, неподходящее состояние соревнования, чужая/отклонённая заявка, неполный протокол, попытка изменить публикацию |
| 500 | Ошибка генерации PDF, хранилища или БД; публикация откатывается |

Пример 422:

```json
{
  "message": "Нужна единственная одобренная заявка спортсмена на это соревнование.",
  "errors": {
    "results.0.athlete_id": ["Нужна единственная одобренная заявка спортсмена на это соревнование."]
  }
}
```

Ошибки новых маршрутов возвращаются без stack trace и внутренних подробностей, в том числе при локальном `APP_DEBUG=true`. Для ошибок 500 используется общее `message`, исходная ошибка остаётся доступна серверному журналу. Валидация сохраняет стандартный `errors`. Для развёртывания всего приложения используйте `APP_DEBUG=false`. Значения `.env` в документацию не копируются.

## Команды OSPanel и тесты

Используйте терминал OSPanel с PHP 8.3+ и Composer из того же окружения:

```powershell
Set-Location C:\OSPanel\home\orenkod
composer install
php artisan migrate --path=database/migrations/2026_10_28_104834_add_results_publication_to_competitions_table.php --no-interaction
php artisan route:list --path=competitions
php artisan test --compact tests/Feature/CompetitionResultsTest.php
```

Миграция добавочная, не удаляет таблицы или записи. Не используйте `migrate:fresh`, `migrate:refresh`, `db:wipe` для основной БД. Тесты не используют `RefreshDatabase`: внутри `setUp` принудительно выбирается SQLite `:memory:`, проверяются драйвер и имя БД, затем создаются только необходимые таблицы. Нужен `pdo_sqlite`. PostgreSQL в рабочей конфигурации остаётся без изменений драйвера.

Зависимости: `dompdf/dompdf ^3.1` для PDF и `laravel/boost ^2.10` в dev по исходному AGENTS.md; транзитивный Symfony YAML выбран совместимым с PHP 8.3. Python-средства проверки PDF устанавливались только во временную игнорируемую папку `tmp/pdf-tools` и для работы приложения не нужны.

Фактически проверено 28.10.2026: все 24 теста проекта прошли (22 теста нового модуля, 195 assertions суммарно); изменённые PHP-файлы прошли синтаксическую проверку и Pint; `composer validate --strict` и `composer check-platform-reqs` прошли на PHP 8.3.30; маршруты зарегистрированы. Новая миграция применена к локальной PostgreSQL, наличие новых полей, индекса и внешнего ключа проверено. Тестовый протокол на 75 участников содержит 8 страниц: кириллица проверена извлечением текста, все страницы отрисованы и просмотрены, обрезки таблицы не обнаружены. Реальные аккаунты/выступления для проверки не создавались. Ручная проверка через HTTP-сессии Postman и нагрузочная проверка блокировок PostgreSQL ещё не проводились.

Покрытие: сохранение/обновление, права и email, недопустимые заявки, дубликаты, все статусы, ошибки мест/баллов/служебных полей, атомарность, неполная публикация, закрытость черновиков, PDF, повторная публикация, откат ошибок генерации/аудита, заморозка публикации и состава, история/изоляция/сортировка/пагинация, назначенные судьи, многостраничная кириллица. Поведение PostgreSQL `FOR UPDATE` под конкурирующей нагрузкой требует отдельного интеграционного окружения; SQLite таких блокировок не моделирует. CSRF в Laravel Feature Tests обычно пропускается самим фреймворком, поэтому реальную сессию/CSRF проверяйте через Postman.

## Проверка через Postman

1. Запустите проект OSPanel, базовый URL `http://orenkod.local`. Установите `Accept: application/json` для коллекции и включите cookie jar. Проверьте, что APP_URL соответствует домену.
2. В local-окружении вызовите `GET /_dev/csrf`. Сохраните cookie сессии и значение `csrf_token`; передавайте его как `X-CSRF-TOKEN` для POST/PUT/PATCH. Если endpoint недоступен, используйте существующий механизм получения CSRF приложения.
3. Выполните `POST /login` с `email`, `password` и CSRF. После входа снова вызовите `GET /_dev/csrf`: существующая авторизация меняет сессию/токен. Cookie jar должен принять новую cookie.
4. Войдите подтверждённым администратором, выполните `POST /switch-role` с `{"role":"admin"}` и актуальным CSRF. Если у учётной записи нет роли, сначала назначьте её существующим административным способом.
5. Подготовьте опубликованное завершившееся соревнование с одобренными участниками, вызовите GET `/participants`. Для существующего процесса создания/публикации соревнования сначала используйте будущие даты; ввод результатов начнётся после `ends_at`.
6. Выполните PUT результатов по приведённой форме. Проверьте GET итоговой таблицы, повторный PUT, недопустимого спортсмена, `dns` без места. GET административного `/protocol` должен отдать PDF с отметкой проекта.
7. До публикации проверьте публичные GET `/results` и `/protocol` без cookies - 404. Попробуйте публикацию с незаполненным участником - 422.
8. Заполните все результаты, выполните POST `/results/publish`. Проверьте публичные таблицу и PDF без cookies. Повторный POST не должен менять файл. PUT после публикации и позднее одобрение заявки должны вернуть 422.
9. В отдельном cookie jar войдите спортсменом, подтвердите email, переключитесь на `athlete`, обновите CSRF после входа. GET `/athlete/results` должен показать только его опубликованные выступления. Подставление чужого `athlete_id` не меняет выборку.
10. Проверьте 401 без сессии, 403 под тренером/спортсменом, 419 для изменяющего запроса без актуального CSRF. Для скачивания PDF можно использовать Postman Save Response.
